# Инструкция по карте репозитория (Aider-вдохновлённая)

Repomap Aider'а — его killer-фича: он строит краткую, токен-оптимизированную ментальную модель всей кодовой базы перед внесением любых изменений. Ты ОБЯЗАН следовать этому паттерну перед редактированием любого файла в незнакомой части кодовой базы.

---

## Когда исследовать репо

Исследуй репо когда:
- Начинаешь работу в новой части кодовой базы
- Тебя попросили отрефакторить или реструктурировать
- Нужно понять, как модули связаны между собой
- Перед написанием кода, который затрагивает несколько директорий

НЕ нужно исследовать когда:
- Делаешь маленькое локальное редактирование файла, который ты уже читал
- Пользователь явно указал на конкретный файл/функцию
- Возвращаешься к работе, которую начал минуту назад в той же сессии

## Протокол исследования

### Фаза 1: Структурное обнаружение (лёгкое)

1. Прочитай листинг корневой директории
2. Определи ключевые директории: `src/`, `server/`, `lib/`, `components/` и т.д.
3. Прочитай `package.json` для зависимостей, скриптов и типа проекта

### Фаза 2: Карта модулей (средняя)

Для релевантных директорий:

```markdown
## Карта модулей: <область>

**Точки входа:**
- `src/index.ts` — главный вход, запуск сервера
- `src/app.ts` — настройка Express/Fastify приложения

**Ключевые файлы по ответственности:**
| Файл | Ответственность |
|------|-----------------|
| `src/middleware/auth.ts` | Валидация сессии, проверка ролей |
| `src/routes/api.ts` | Определения API-маршрутов |
| `src/utils/db.ts` | Пул соединений с БД |

**Общие утилиты:**
- `src/utils/` — 12 файлов (auth, db, validation и т.д.)

**Поток данных:**
Запрос → middleware → handler маршрута → сервис → база данных
         ↓
      auth.ts валидирует сессию
```

### Фаза 3: План для реализации (когда нужно)

Перед написанием кода выведи:

```markdown
## План

**Цель:** <однострочное описание>

**Файлы для изменения:**
1. `src/utils/auth.ts` — добавить функцию `verifyBackupCode()`
2. `src/routes/auth.ts` — добавить endpoint `POST /api/auth/verify-backup`

**Файлы, которые НЕ трогать (даже если связаны):**
- `src/middleware/csrf.ts` — изменения не нужны, endpoint CSRF-exempt

**Зависимости:**
- `src/utils/totp.ts` — вызывать `verifyTOTP()` перед проверкой backup code
- `src/utils/audit.ts` — логировать проверку backup code

**Риски:**
- ⚠️ Изменение auth flow — нужно проверить, что все существующие тесты проходят
```

---

## Правила глубины исследования

| Размер изменения | Глубина исследования | Лимит времени |
|---|---|---|
| **Маленький** (<50 строк, 1-2 файла) | Только Фаза 1 | <30 секунд |
| **Средний** (50-200 строк, 3-5 файлов) | Фаза 2 | <2 минут |
| **Большой** (>200 строк, 5+ файлов) | Фаза 3 + поиск существующих тестов | <5 минут |

## Интеграция с Semantic Search

Инструмент `semantic_search` в NoCowboy может находить связанный код по смыслу. Используй его как дополнение к структурному исследованию:

```
1. Фаза 1: Чтение структуры директорий
2. semantic_search("authentication flow") → найти связанный код
3. Фаза 2: Построить карту модулей, используя структурные + семантические результаты
```

## Анти-паттерны

- ❌ Чтение 50 файлов перед тем, как сделать правку в 5 строк
- ❌ Внесение изменений без понимания, какие другие файлы зависят от изменяемого
- ❌ Слепое редактирование файлов без чтения окружающего кода для контекста
- ✅ Чтение целевого файла + его импортов + любых файлов, которые импортируют его
- ✅ Поиск тестов, связанных с файлом, перед его изменением

## Deep Context Mode (NoCowboy)

Когда `indexing.enabled` установлен в true в nocowboy.json, repomap
авто-генерируется перед каждым шагом агента и внедряется в контекст. Repomap включает:

- Структуру директорий с количеством файлов и строк
- Ключевые зависимости, обнаруженные из import/require
- Метки ответственности, авто-определённые из имён директорий

Агент использует это для:
- Понимания структуры проекта перед изменениями
- Нахождения правильного файла для редактирования
- Избегания правок, которые сломают границы модулей
