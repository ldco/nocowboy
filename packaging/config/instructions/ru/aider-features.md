# Aider-вдохновлённые DX-фичи

Справка по: атомарные изменения, авто-коммит, conventional commits, lint-on-edit, git-интегрированный workflow.

---

## 1. Принцип атомарных изменений

Aider делает одно логическое изменение за раз. Ты ОБЯЗАН следовать этому паттерну:

1. Понять запрос → определить минимальный набор файлов для изменения
2. Сделать ОДНО логическое изменение (может затрагивать несколько файлов, но по ОДНОЙ причине)
3. Показать diff-summary того, что изменилось
4. Закоммитить изменение с conventional commit сообщением
5. ЗАТЕМ (и только затем) перейти к следующему изменению

**Анти-паттерн**: Сделать 5 несвязанных изменений в 10 файлах за раз, затем один большой коммит.
**Паттерн**: Изменение → review diff → коммит → следующее изменение.

## 2. Протокол авто-коммита

После КАЖДОГО значимого изменения кода (не шум от конфигов/вызовов инструментов), ты ОБЯЗАН:

```bash
git add <изменённые файлы>
git commit -m "<type>(<scope>): <описание>"
```

Формат сообщения коммита (Conventional Commits):
- `feat:` — новая фича
- `fix:` — исправление бага
- `refactor:` — изменение кода, которое не чинит баг и не добавляет фичу
- `style:` — форматирование, пропущенные точки с запятой и т.д.
- `docs:` — только документация
- `test:` — добавление или исправление тестов
- `chore:` — процесс сборки, инструментарий, зависимости

**НЕ коммить когда:**
- Изменение в процессе (пользователь явно сказал «draft» или «WIP»)
- Изменение — это просто вызов инструмента (чтение файлов, поиск)
- Пользователь сказал «не коммить»

**Правило**: Если ты отредактировал файлы и результат — полное, рабочее состояние → закоммить.

## 3. Пре-коммит верификация

Перед коммитом проверь:
- [ ] Код компилируется / проходит typecheck (`bun run typecheck` или эквивалент)
- [ ] Нет забытых debug-принтов, console.log или TODO комментариев
- [ ] Связанные тесты проходят (запусти конкретный тестовый файл, если возможно)
- [ ] Нет секретов, API-ключей или паролей в diff

Если верификация не прошла → исправь → перепроверь → коммить.

## 4. Пост-редакционный lint-цикл

После каждого изменения кода запускай линтинг. Если линт падает с авто-исправляемыми проблемами:

```
1. Отредактировать файлы
2. Запустить: npm run lint -- --fix (или эквивалент)
3. Если всё ещё падает: исправить оставшиеся проблемы вручную
4. Запустить typecheck
5. Закоммитить
```

## 5. Git Diff перед коммитом

Перед коммитом покажи пользователю краткий diff-summary:

```
## Готово к коммиту
feat(auth): добавить 2FA backup codes

Изменено:
  M  server/utils/totp.ts     (+42, -3)
  M  server/routes/auth.ts    (+15, -1)
  A  server/utils/backup.ts   (+89)

Верификация:
  ✓ TypeScript: нет ошибок
  ✓ Тесты: 12 прошло, 0 упало
  ✓ Линт: чисто
```

## 6. Протокол отмены

Если пользователь говорит «отмени», «revert», или «мне не нравится это изменение»:

```bash
git reset --hard HEAD~1   # Если последний коммит был изменением AI
# ИЛИ
git checkout -- <файл>     # Если ещё не закоммичено
```

Затем подтверди, что было отменено.

## 7. Отслеживание состояния сессии

Отслеживай, что сделано в этой сессии:
- Созданные/изменённые файлы (с количеством строк)
- Сделанные коммиты (с сообщениями)
- Результаты линта/тестов
- Открытые вопросы / отложенные решения

Выведи summary сессии когда попросят или в конце сложных задач.

## 8. Лимиты размера изменений

- **Маленькое (<50 строк)**: Прямое редактирование + авто-коммит
- **Среднее (50-200 строк)**: Редактирование + линт + тест + коммит
- **Большое (>200 строк)**: Разбей на несколько атомарных коммитов, каждый <200 строк

Если изменение >200 строк, спроси себя: можно ли разбить на 2+ логических коммита?

## 9. Conventional Commit Scopes

Используй эти scopes в зависимости от структуры проекта:
- Scope = основная директория/модуль, который затронут
- Примеры: `fix(auth): ...`, `feat(api): ...`, `refactor(db): ...`
- Если не уверен — опусти scope: `fix: ...`

## 10. Интеграция с NoCowboy Git MCP

Git MCP предоставляет структурированные git-операции. Предпочитай использовать:
- `git_git_status` — проверка рабочего дерева перед коммитом
- `git_git_diff` / `git_git_diff_staged` — review изменений
- `git_git_add` — добавление файлов в stage
- `git_git_commit` — коммит с сообщением
- `git_git_log` — недавняя история для контекста

Используй `bash` с `git` командами, если MCP недостаточно.
